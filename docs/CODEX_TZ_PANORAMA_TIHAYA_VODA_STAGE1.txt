GAGARIN PANORAMA STUDIO — «ПРОТОКОЛ „ТИХАЯ ВОДА“»
ЭТАП 1. РАСШИРЕНИЕ ДВИЖКА И ИГРАЕМЫЙ ВЕРТИКАЛЬНЫЙ СРЕЗ
24.10.2026

ТВОЯ РОЛЬ
Ты — ведущий разработчик Gagarin Panorama Studio. Твоя задача — сохранить существующий универсальный редактор и игровую экспортную систему, добавить недостающие функциональные возможности для сюжетных игр и собрать полностью проходимый вертикальный срез арктического симулятора/психологического хоррора по главам 1–3 приложенного сценария «Протокол „Тихая вода“». Не переписывай художественный текст от себя и не пытайся собрать всю игру на этом этапе.

ВХОДНЫЕ МАТЕРИАЛЫ
1. Имеющиеся исходники Gagarin Panorama Studio, актуальная версия 2.7 Director (или последняя обнаруженная рабочая ревизия). Сначала найди фактическую структуру кода и состав возможностей; не доверяй номерам версии без проверки.
2. Сценарий ARCTIC_STATION_SCENARIO.txt — творческий источник истины по сюжету, логике и событиям. Если файл не лежит в папке проекта, сообщи об этом в итоговом отчёте; НЕ выдумывай содержание, которого не видел.
3. Существующие демонстрационные проекты, PROJECT.zip / GAME.zip и данные режиссуры, если они находятся в исходниках.

ОБЩИЙ ПРИНЦИП
Редактор — самостоятельный продукт. Нельзя жёстко зашить «Тихую воду» в движок или ломать другие игры ради этой одной. Реализуй расширения как универсальные инструменты, а сценарий первых глав — как отдельный проект, созданный на их основе. Выбирай самый простой поддерживаемый способ; не заводи новую сложную архитектуру, фреймворк, серверную часть или зависимости без реальной необходимости.

ЖЁСТКИЕ ОГРАНИЧЕНИЯ
- Не удалять и не ухудшать функции 2.7 Director: пространственные звуковые точки, катсцены/таймлайны, события запуска, состояния объектов, субтитры, сообщения, камера, глобальные переменные, демонстрационная комната, экспорт проекта/игры с сохранением исходного проекта.
- Сохранить возможность обратного импорта экспортированного проекта, редактирования новых сущностей и повторного экспорта.
- Не ломать старые проекты без новых полей: миграция схемы или безопасные значения по умолчанию.
- Встраиваемая браузерная игра. Предпочтительно отсутствие обязательного backend; по возможности поддержка запуска готового экспорта локально из index.html с предупреждением о браузерных ограничениях, если они неизбежны.
- Сохранить текущий стиль интерфейса и компактность приложения. Не делать игрового редактора, который требует сотни ручных кликов для одной простой сцены.
- Вся игровая логика должна быть данными проекта, а не разрозненными условными операторами, привязанными к конкретной игре.
- Не записывать видеозаглушки и аудиозаглушки как «готовый художественный контент»; пометить их в проекте для замены.

A. НОВЫЕ УНИВЕРСАЛЬНЫЕ ВОЗМОЖНОСТИ РЕДАКТОРА

A1. КВЕСТОВАЯ СИСТЕМА
- Сущность Quest: id, название, описание, список этапов, условия начала, условия завершения, видимость игроку, автоматическое/ручное обновление.
- У этапа: id, текст задачи, условия (флаги, предметы, мини-игра, видео, взаимодействие), событие OnStart/OnComplete, необязательный маркер объекта.
- Один активный основной квест; поддержка параллельных необязательных квестов. Журнал задач у игрока, где выполненное сохраняется.
- Условия AND, OR, NOT, ==, !=, <, >, >=, <= для простых типов. Без исполнения произвольного JS из пользовательских данных.
- Редактор условий через контролы, без необходимости писать выражения вручную.

A2. ИНВЕНТАРЬ И ИНТЕРАКТИВНЫЕ ПРЕДМЕТЫ
- Данные предмета: id, заголовок, описание, при необходимости иконка/изображение; флаг уникальности.
- Действия: взять, осмотреть, применить к объекту, проверить наличие, убрать/вернуть по событию.
- Предметы отображаются в простом игровом интерфейсе. Применение предмета к объекту вызывает событие; неверное применение сообщает игроку, что действие не подходит, без софтлока.
- Ключ, предохранитель и кассета в вертикальном срезе должны быть настоящими предметами с отслеживаемым состоянием.

A3. МИНИ-ИГРЫ, БЕЗ НЕОБРАТИМЫХ ПРОВАЛОВ
- Универсальный модальный либо встроенный в панораму UI. События OnStart, OnWin, OnFail, OnExit.
- Настраиваемые редактором шаблоны для первого этапа: (1) последовательность действий/кнопок; (2) переключатели с целью по суммарной нагрузке; (3) сопоставление элементов/drag-and-drop или доступный альтернативный выбор; (4) аналоговая настройка ручки/ползунка по целевому диапазону.
- У всех: понятные правила, текстовая подсказка, возможность повторить, отсутствие зависания квеста после ошибки, клавиатурная/мышиная доступность.
- Состояние мини-игры записывать в сохранение после победы. Остальные перечисленные в сценарии механики не добавлять на данном этапе без нужды.

A4. ДОКУМЕНТЫ И АРХИВ
- Отдельная сущность Document: id, title, body, category, optional image, условия доступности, отметка прочтения.
- Интерфейс чтения/повторного открытия, список найденных документов, корректная прокрутка и кириллица.
- Документы хранятся в проекте как редактируемые строки, а не встроены в UI.

A5. ВИДЕОПРОИГРЫВАТЕЛЬ
- Объект Video: id, заголовок, файл/asset, субтитры или текстовые таймкоды, pause/play, OnStart/OnEnd.
- Встроенный показ на экранном мониторе/магнитофоне или поверх игрового интерфейса с возможностью вернуться к сцене.
- Поддерживать браузерные совместимые MP4/WebM, описать особенности кодеков/автозапуска. Медиа могут не входить в демонстрацию: вместо V1 отображать ЗАМЕЩАЮЩИЙ КЛИП/СТОРИБОРД, отмеченный явно как временный.
- В проекте оставить слот для замены V1 реальным видео без изменения квестов и триггеров.

A6. ВАРИАНТЫ КОМНАТ И СОБЫТИЯ ВОЗВРАТА
- Для логической комнаты поддержать несколько визуальных/объектных вариантов, выбираемых условием/переменной (например KITCHEN_NORMAL / KITCHEN_PHOTO_4; ARCHIVE_NORMAL / ARCHIVE_AFTER_V1).
- Не создавать полноценную глобальную симуляцию пространственно-временных путешествий: это ручные авторские изменения локаций.
- События first enter / each enter / return after flag / first interaction. Защитить от повторного бесконечного срабатывания одноразовых сюжетных событий.
- Переключение изображения, интерактивных зон, состояния предметов и ambient-звуков должно быть детерминированным.

A7. СОХРАНЕНИЯ
- Один или несколько слотов в localStorage/IndexedDB, выбрать по фактической архитектуре. Сохранять: текущую комнату, квесты, этапы, инвентарь, прочитанные документы, просмотренные видео, флаги, состояния комнат/объектов и одноразовые события, результаты мини-игр.
- Контроль версии данных сохранения и безопасный fallback для старых проектов.
- Кнопки «Продолжить», «Новая игра» и «Сохранить» в экспортируемой игре.
- Не писать реальные файлы сохранения на диск без разрешения пользователя. Не удалять сохранения в качестве хоррор-эффекта.

B. ВЕРТИКАЛЬНЫЙ СРЕЗ «ТИХАЯ ВОДА», ГЛАВЫ 1–3

ИГРОВОЙ ЦИКЛ — ОКОЛО 20–30 МИНУТ БЕЗ ИСКУССТВЕННОГО ЗАТЯГИВАНИЯ
1. Старт в жилом модуле. Игрок принимает смену, осматривает шкаф, берёт бейдж, находит записку о ключе под кружкой, осваивает чайник.
2. Кухня. Мини-игра с приготовлением чая. При первом/повторном посещении холодильника изменяется фотография с тремя людьми на фотографию с четырьмя, без обязательного скримера. Если фотографии отсутствуют, сделать временные схематичные макеты с крупной пометкой «placeholder».
3. Диспетчерская. Сверить показания/дату, электронно принять смену. В бумажном журнале есть тревожный след чужой/будущей подписи.
4. Склад. Найти ключ, получить предохранитель №3. Подключить это к настоящему инвентарю.
5. Электрощитовая. Мини-игра по балансировке нагрузки; после успеха выставляется флаг и квест обновляется.
6. Лаборатория. Сопоставить P-14, P-15, P-16; после успешной маркировки принтер выдаёт заявку P-17 с завтрашней датой. P-17 физически отсутствует.
7. Радиорубка. Настроить диапазон и отправить отчёт. Радиореплика Белова «в этот раз» (можно текстовыми субтитрами до записи озвучки).
8. Архивный пакет №12. Найти изменившуюся маркировку ящика на складе; открыть пломбу в правильной последовательности 2–4–1–3; найти VHS.
9. Архив. Вставить найденную кассету и просмотреть V1. Пока нет видеоматериала — временная титрованная сценка с длительностью/событием окончания; не выдавать её за реальный готовый ролик.
10. После окончания V1 изменяется состояние шкафа, появляется надпись «НЕ ДЕЛАЙ ВИД, ЧТО МЫ НЕ ЗНАКОМЫ». На этом заканчивается демонстрационный отрезок. Вывести спокойный экран «Продолжение смены — в полной версии» и оставить возможность свободно вернуться в комнату.

СЦЕНЫ ДЛЯ СРЕЗА
Минимально необходимые логические комнаты: жилой модуль, кухня, центральный коридор, диспетчерская, электрощитовая, склад, лаборатория, архив. Можно использовать временные фоны и простые панорамные изображения/плоские текстуры с корректными кликабельными зонами. Не трать ресурсы на художественную 3D-графику до работающей механики.

КВЕСТЫ
Q1 «Принять смену»; Q2 «Утренний обход»; Q3 «Разобрать архивный ящик». В интерфейсе отображаются понятные цели и подцели; события сюжетной странности не останавливают движение игрока. Одноразовые события не проигрываются заново после возврата, если сюжет не требует повторной версии.

КЛЮЧЕВЫЕ ФЛАГИ
CHAPTER: 1–3;
Q1_DONE, Q2_DONE, Q3_DONE;
HAS_STORAGE_KEY, HAS_FUSE_3, HAS_VHS_V1;
TEA_DONE, POWER_BALANCED, CORES_LABELED, RADIO_REPORT_SENT;
PHOTO_CHANGED, P17_PRINTED, BOX12_OPENED, V1_WATCHED, ARCHIVE_MESSAGE_SHOWN.
Названия можно адаптировать к существующему стандарту редактора, но все связи должны быть видны и доступны для правки.

C. РЕДАКТОРСКИЙ UX
- В редакторе должны существовать понятные места для настройки квестов, инвентаря, мини-игр, документов и видео.
- Не обязательно создавать пять новых верхнеуровневых вкладок; допустим один функциональный раздел «Игровые системы» с подразделами. Важно не раздувать уже имеющийся UI.
- Для событий можно выбрать существующие действия плюс новые: grant/remove item, start/advance/complete quest, open minigame, open document, play video, set room variant, save checkpoint.
- Новые сущности должны участвовать в экспорт/импорте проекта и GAME.zip.

D. ПРОВЕРКА ГОТОВНОСТИ
1. Старый демопроект редактора открывается и работает без новых полей.
2. Все ранее реализованные редакторские возможности режиссуры сохранены.
3. Каждый из трёх квестов проходится в экспортированной игре до конца; достижим экран конца вертикального среза.
4. Можно сохранить игру между заданиями, перезагрузить страницу и продолжить без повторения одноразовых событий.
5. Можно заменить V1 на настоящий видеофайл через редактор без переписывания логики.
6. Мини-игры завершаются штатно, при неправильном ответе доступны повтор/подсказка.
7. Обратный импорт проекта из экспорта сохраняет инвентарь, квесты, варианты комнат, медиаслоты и события.
8. Ничего не требует внешнего сервера, если раньше проект был самодостаточным (либо ограничение явно описано).

E. ВЫХОДНЫЕ АРТЕФАКТЫ
- Обновлённый исходный редактор.
- Отдельный редактируемый проект игры «Протокол „Тихая вода“ — вертикальный срез».
- Экспортированная запускаемая игра и исходный проект в форматах, предусмотренных текущей Studio.
- CHANGELOG с перечнем изменений; инструкции как открыть и изменить сценарий, заменить медиа и экспортировать.
- Короткий отчёт: что реализовано, что не реализовано, какая проверка реально выполнялась. Не объявляй результат рабочим без запуска.

НЕ ДЕЛАТЬ НА ЭТОМ ЭТАПЕ
- Не создавать всю 100–125-минутную игру, финалы и поздние главы.
- Не придумывать сюжет, диалоги, документы или лор вместо сценариста.
- Не генерировать огромный набор ассетов, пока механика не готова.
- Не заменять работающий редактор новым проектом «с нуля».
- Не тратить время на системы монстров, ИИ врагов, полноценный 3D-мир, боёвку или физику.

ПОРЯДОК РАБОТЫ
Изучи существующий проект и структуру данных -> внеси совместимые универсальные улучшения -> построй на них первые 3 главы отдельным проектом -> экспортируй и проверь полный цикл от старта до окончания -> отчитайся по реально достигнутому результату. Работай автономно; запросы к пользователю нужны только при блокирующих отсутствующих исходниках/контенте.
